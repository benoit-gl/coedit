# Independent packed-record review

Reviewed scratch `/workspace/work/merge10-packed-prototype` at its completed H500 audit checkpoint. No repository edits, heavy workload reruns, or benchmark runs were performed. I read both worker versions, fixture builders, primitive, source snapshot, correctness cases, measurement journals and `transaction-audit-h500.json`; independent bounded checks parsed manifests/source hashes and decoded the retained original H500 document's changes once.

Verdict: the experiment supports a storage-representation result for this exact input. I found no silent record loss, logical UUID collision, cross-command batching, or successful immutable-body rewrite in the reviewed valid measured path. It does not establish a packed full carrier, preservation of native command provenance, or production eligibility.

## Findings

1. **P2, robustness defect outside measured inputs: `load` does not enforce the bounded width.** `packed-store.mjs:82` validates `create(width)` against `[1,64]`, but `load(encoded,width)` at line 86 forwards any width. Loading valid bytes with width zero and then appending any new record makes the loop at line 111 never advance; negative widths also fail to advance toward termination. This was established by source inspection without running an infinite loop. Validate width in the shared constructor/load path. Existing H16/H500 workers always supply 1 or 64, so their outputs are unaffected.

2. **P2 qualification gap, explicitly disclosed: full-carrier command/provenance validation is absent.** `append` accepts individually canonical records without requiring complete closed commands or checking their accepted-base/native dependency authorization. Its history validator enforces immutable scalar storage, not `nativeDocument.ts` command semantics. Protocol validation is subsequently called by the harness, outside timed build/load. Both trie and packed arms are storage primitives, so this is a reasonably matched primitive comparison; neither is a current-versus-packed full-carrier comparison. Do not report their timings/memory as complete carrier improvement. Native bootstrap/provenance metadata from the original carrier is deliberately not replayed.

3. **P2 evidence limit, explicitly disclosed: H500 has build-retention memory only.** `measure500-worker.mjs:14–23` samples post-GC growth after parsing/decoding the entire input tape. This incremental figure excludes the tape's existing retained cost and includes representation-specific native caches, accepted records, packed locator maps, and instrumentation. All variants receive the same exact tape; the candidate's extra locator cache is included, so I found no free native locator or missing packed cache charge. Packed arms additionally retain 502 receipt arrays while trie does not, a small asymmetry against packed. `sameProcessReloadMs` is collected with the separately loaded `raw` document and decoded native history still live at lines 27–40; it is verification timing, not fresh-load memory, isolated load timing, or a controlled one/two-carrier overlap/release experiment. No H500 load-retention/peak-memory ratio is justified. H4/H16 fresh-process loads are a distinct, smaller experiment.

4. **P3 evidence/coverage limits: single fixed-order observations and version distinction.** Workers run trie, width-one and command-pack in that order once. Build time includes progress logging and receipt instrumentation. Numbers can describe these runs but do not establish repeatable latency distributions or isolate every source of process-memory growth. H4/H16 bind to archived `v1/packed-store.mjs`, whose `resolve` returned the decoded accepted-map entry; current/H500 `resolve` genuinely decodes bytes at unit/slot and checks the logical UUID. The v1 manifest hashes match, and `correctness16-v2.json` records the current-reader correctness checkpoint; distinguish old measurement source from current-reader verification.

5. **P3 coverage/harness caveat: source extraction and hostile-case labels are broader than their checks.** `runtime.mjs:21` overwrites its extraction Map by UUID without checking for an unequal prior body. This would hide an equivocation in a hostile source document. It did not hide anything in the H500 fixture: an independent comparison of *all* original native record-set operations found exactly 3,511 distinct UUIDs and exactly the replay tape keys. Also, the correctness test named “reject native malformed-conflict on cold load and atomic merge” only calls cold load for that particular branch; its other branches check merge atomicity. Candidate merge does call the same validator/collector before adoption, but that named branch is not itself an executed merge-atomicity test. Neither observation invalidates the reported valid fixture.

## Input, identity and command-boundary assessment

H16 contains 18 groups and 122 unique canonical records: genesis 1, seed 9, then sixteen 7-record edits. H500 contains 502 groups and 3,511 unique canonical records: genesis 1, seed 10, then five hundred 7-record edits. H500 kinds are 502 manifests, 1,003 live records, 501 each contexts/envelopes/payload effects, 252 runs, 250 erases and one generation. Independent fixture checks matched every non-genesis manifest's exact context/envelope/evidence/operation member Refs to its group's members, checked shared batch/effect identities, and checked fixture semantic hashes. No final-visible-only record selection occurred.

The independent original-H500 native-op check found the exact same 3,511 canonical keys, with semantic SHA256 `234827865c404f1ba7451d29aedec6bdb262a5eb6b074ba125f7f3ca6498ebd7`. Thus the extractor caveat above is closed for this fixture. Source snapshot hashes and archived v1 harness hashes all matched their manifests. Current H500 worker/store/fixture hashes also match the completed journal rows.

The completed transaction audit checks each of the three saved H500 artifacts against all 502 exact fixture groups, with each command change depending on the preceding change. Each primitive retains 503 native changes: its own bootstrap plus 502 groups. The original full carrier has 502 native changes because its genesis shares its native bootstrap transaction. This is a documented replay representation difference, not dropped command history. All three replay controls share it.

Width-one uses 3,511 physical units and 3,514 native operations; command-pack uses 502 units and 505 operations. Trie uses the same 3,511 logical records and 107,924 operations including 104,335 maps. The width-one control is necessary: trie-to-packed reduction combines removal of the deep trie with packing, whereas width-one-to-command-pack isolates packing within the scalar-unit representation. Encoded H500 sizes are respectively trie 648,404, width-one 584,576 and command-pack 316,327 bytes.

Logical Refs remain `[record UUID, canonical-record commitment]`. Physical unit keys commit the whole canonical byte array; slots derive from sorted UUIDs. Cold collection checks each scalar alternative, each record canonical form, pack hash, ordering/uniqueness, and unequal reuse of a logical UUID. Multiple identical logical copies are allowed only with equal bodies; the selected location can change without changing the Ref. Current `resolve` checks both commitment and UUID against actual unit bytes. No cryptographic hash-collision resistance beyond SHA256's normal assumption is claimed.

## History, concurrency, Origin and malicious edits

The current immutable-history validator reads every decoded native change on load/merge. It restricts bootstrap and subsequent operations, rejects predecessors/deletes/map replacements, and validates all historical scalar writes, including content later hidden from the winning view. Merge stages state and checks the accepted-record subset before adoption. Append validates every supplied record/duplicate before one native mutation; an equal duplicate is a no-op, and an unequal UUID body fails before publication. The reviewed tests cover idempotence, mixed valid/conflicting append atomicity, separately valid equivocation branches, actual same-key concurrent equal scalar conflicts, disjoint additions, malformed conflict values, deletion/replacement attempts, metadata/layout and foreign lineage. They are storage-conflict tests, not separately authored concurrent full-carrier commands.

H16 checks all retained native prefixes and old-root text/Origin projections; its real fixture includes BMP/astral text and multiple insertion Origins. H500 checks five native prefix views, all receipt hashes, all 501 non-genesis historical logical-root text/Origin projections after reopen, and all exact logical Refs through current unit/slot reads. The independent per-command transaction audit strengthens its native-prefix preservation claim. H500 uses a single Origin and regular ASCII insert/delete history; it cannot by itself establish arbitrary attribution/non-inheritance behavior, paste-origin preservation, restore/copy/split semantics, stale revision refusal, cursor identity behavior, many-author frontier costs, or adversarial UUID distribution behavior. Those remain full-carrier qualification work, not failures demonstrated here.

The existing scoped wording is appropriate. No high-severity defect was found in the measured storage paths, and no evidence supports treating this prototype as an incremental production carrier implementation yet.
